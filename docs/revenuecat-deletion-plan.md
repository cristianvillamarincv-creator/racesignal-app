# RevenueCat customer deletion: verified facts, plan and development results (2026-10-09 to 2026-10-10)

**Implemented and verified on the DEVELOPMENT project only (section 8).** Production is untouched: no production secret, function, migration, RevenueCat record or setting has changed, and Build 18's `delete-account` is still what production runs. This resolves the open item in `docs/release-1.1-checklist.md` ("Tracked before submission") and the pending sentence on the Privacy page in `site/privacy/index.html`. Publishing the site stays paused until this is decided.

## 1. What was verified

**RevenueCat's documentation (read 2026-10-09)**
- **REST API v2, "Delete a customer":** `DELETE https://api.revenuecat.com/v2/projects/{project_id}/customers/{customer_id}`. Required key permission: `customer_information:customers:read_write`. Success is **200 "deletion was queued and will be processed asynchronously"** (so 200 means requested, not finished), body `{object: "customer", id, deleted_at}`. Other codes: 400, 401, 403, 404, 409, 422, 423, **429** (rate limit), 500, 503. Rate-limit domain "Customer Information", default 480 requests a minute. `customer_id` up to 1500 characters. The page does not say which data is removed.
- **REST API v1, "Delete Customer":** `DELETE https://api.revenuecat.com/v1/subscribers/{app_user_id}`; "permanently deletes a customer"; queued asynchronously; **200 or 404 are both treated as success** for retry-safe flows; the id **may be an aliased App User ID**. Needs a secret key.
- **Keys:** public SDK keys (what the app and the `signal` function use today, `REVENUECAT_PUBLIC_API_KEY`) "make non-potent changes" and cannot delete. Secret keys (`sk_`) are project-wide server-side keys that can delete customers; never embed them in an app; rotate them. A v2 key can be limited to specific permissions.
- **Effects (RevenueCat staff, community forum; not in the formal docs):** deleting a customer through the API or dashboard also deletes its historical purchase data; if the person later restores purchases with the same store account, the data is re-created. Deleting a customer does **not** cancel a store subscription (Apple's subscription and records are untouched).
- **GDPR page:** RevenueCat is a processor and we are the controller, so our policy must disclose what we pass to it. It gives **no retention period or deletion timeline** and points to compliance@revenuecat.com for erasure requests and the Data Processing Addendum.
- **Not documented anywhere I could find:** whether deleting a customer also removes its **anonymous aliases**, how long backups or derived metrics keep data, and whether the v2 call behaves exactly like v1. These need an empirical test on the development project (section 4) and, for retention, a short written question to RevenueCat (section 6).

**What our deletion leaves behind today (development RevenueCat project and database, read-only, 2026-10-09)**
- The development project holds 24 customers: **10 keyed by a Supabase user ID** and 14 anonymous (`$RCAnonymousID:…`). The development database has **5 auth users**; five RevenueCat customers have no matching account, so **account deletion leaves the RevenueCat customer behind** (confirmed again, not only inferred).
- A sample orphan (the account deleted on 2026-10-08): no entitlements, no purchases. It holds only the app user ID, first and last seen times, app version, country, platform and OS version. The app sets no RevenueCat attributes (no email, name or phone), so none exist.
- The production project holds 27 customers (7 keyed by a user ID, 20 anonymous). Matching those against production accounts to count orphans needs a read of production auth users, so it is a gated step below, not done.
- **Anonymous customers** are created by the SDK on a device before anyone signs in. They carry a random id plus the same device metadata and no account identifier. Whether signing in merges them into the account's customer (an alias) or leaves them separate is exactly what the test in section 4 settles.

## 2. Recommended design

1. **Credential.** A RevenueCat **v2 secret key limited to `customer_information:customers:read_write`**, one per RevenueCat project (development, production), created by you in each dashboard and never typed into chat. Stored as the Supabase function secret `REVENUECAT_SECRET_API_KEY`, plus `REVENUECAT_PROJECT_ID` (development `projb98e9609`, production `proj48e9ded9`). The existing public key stays for `signal`. A small helper like `supabase/prod/set-apple-secrets.py` (silent prompt, dry-run default, typed confirmation, read-back digest, previous secrets untouched) sets them.
2. **`delete-account` order: delete the account first, then RevenueCat.** The auth user is the thing that must never be blocked or left half-done, so RevenueCat runs only after `auth.admin.deleteUser` succeeded. If the account deletion fails, RevenueCat is not touched.
3. **The RevenueCat call:** `DELETE /v2/projects/{id}/customers/{encodeURIComponent(userId)}`, 8 second timeout (same bound `signal` uses for its RevenueCat lookup), **one retry** on a network error, 429 or 5xx. **200 and 404 both count as done.** Anything else (401/403 key problem, 4xx, still failing) is reported, never thrown.
4. **Result, never a failure of the deletion.** The response keeps `deleted: true` and gains `revenueCat: "requested" | "failed" | "not_configured"` (the same pattern as `appleRevocation`). Old builds ignore the extra field, so **Build 18 keeps working** against the new function. Logs carry only the status and the user ID (already a UUID in our logs), never the key.
5. **Failure path: honest wording, no queue for now.** A failure leaves one orphaned customer that holds no email or name. We say so in the policy and handle it on request (and by the backfill below). A durable retry queue is possible later but adds a table and a scheduled job for a rare, low-sensitivity case; not recommended for 1.1.
6. **No app change needed** and nothing new to show the user. Deleting the account does not cancel the App Store subscription; the existing deletion alert already says so.
7. **One risk to test, not assume:** after the server deletes the customer, the app on the phone still has that user ID configured in the RevenueCat SDK until sign-out finishes. A refresh in that window could re-create the record. If the test shows that happens, the fix is small (log the SDK out right after `delete-account` returns, before other awaits).
8. **Existing orphans: a separate, owner-approved backfill.** A dry-run-by-default script lists RevenueCat customers keyed by a user ID with **no matching account** and no active entitlement or purchase, and deletes them only on a typed confirmation. Development first (5 orphans, all without purchases). For production, run the read-only match first and review the list with you; deletion is irreversible, so any orphan with purchase history is excluded and shown to you instead.
9. **Anonymous customers:** leave them alone unless the section 4 test shows a signed-in user's aliases survive deletion. If they do, either use the v1 call (it accepts aliases) or disclose them, as in section 5.

## 8. Development results (2026-10-10; development Supabase and RevenueCat projects only)

**Built.** Migration `0012_revenuecat_deletion_requests.sql`; `functions/_shared/revenuecat.ts` (the v2 calls), `revenuecatCleanup.ts` (record and sweep logic), `revenuecatStore.ts`; `delete-account` calls it after the account is deleted; new function `revenuecat-cleanup` (sweep, service key only); dev helpers (`supabase/dev/set-dev-secret.sh` now passes secrets through a private temp file, never on the command line; `dev-supabase.sh` can deploy the new function; `revenuecat-backfill-dryrun.py`). Deno: 38 tests (30 for these modules, including 4 for reappearance and 1 for needsAttention, plus the 8 Apple tests); Python: 5 for the dry-run script.

**How it behaves.**
- The account is deleted first and always succeeds. A row for the account id is written to `revenuecat_deletion_requests` **before** the deletion (so a crash cannot lose it), and updated after: `accepted` (RevenueCat queued it, still pending), `failed` (with a short code such as `http_401`, `timeout`, `not_configured`) or `verified`. The response carries `revenueCat: requested | failed | not_configured`; old clients ignore it, so Build 18 stays compatible.
- **An accepted request stays pending until a lookup returns 404.** The sweep (`revenuecat-cleanup`) looks each open request up, re-requests it when the customer is still there after 15 minutes (or when the earlier request failed), stops after 10 attempts but leaves the row visible, and never touches a customer whose account still exists. Verified rows are looked at again for 7 days (a customer can reappear) and removed after 30 days.
- The row holds only the old account id, a status, counters and a short code: no email, name or RevenueCat response.

**Verified on throwaway development accounts (real function, real RevenueCat dev project).**
1. *Failure is recorded and retried without any user action.* With no RevenueCat key configured, deleting a throwaway account still succeeded (`deleted: true`, `revenueCat: "not_configured"`), the account was gone, and the request was recorded as `failed / not_configured`. After the key was set, one sweep re-requested it (`accepted`), and the next confirmed the customer gone (`verified`, 404).
2. *Normal path.* A second throwaway account: `revenueCat: "requested"`, row `accepted`, the customer and its alias gone within seconds, confirmed by a lookup (`verified`).
3. *Anonymous alias.* Signing in merges the anonymous id into the account's customer: looking up the anonymous id returned the account's own customer, and **deleting the customer removed the anonymous alias too** (both returned 404 afterwards). A customer for an install that never signed in stays a separate anonymous record, not linked to any account.
4. *The customer can reappear.* After deletion, one subscriber call of the kind the app's SDK makes with the old account id (HTTP 201) created the customer again with a new first-seen time. This is a real risk, so the sweep now rechecks recently verified rows: it found the customer, deleted it again (`attempts` 2, `last_error: reappeared`, pending) and the next sweep verified it gone. On a phone the window is short (the SDK is logged out when sign-out completes), and the recheck covers it.
5. *Safety.* A sweep never deletes the customer of an account that still exists (a row written for a live account was dropped and the customer was untouched). The sweep refuses the anon key, a signed-in athlete's token and no key (401). The key does not appear in any response, row or test output.

**Still open, deliberately.** (a) **The sweep is not scheduled.** It runs when someone invokes it; before the privacy sentence can be published, production needs a schedule (for example `pg_cron` + `pg_net` with the key in Vault, every 30 minutes) and an alert or a weekly look at rows that are not `verified`. (b) A real phone test of Settings → Delete account with a Test Store subscription (the throwaway tests above call the same function without the app's SDK). (c) RevenueCat's own retention after deletion is not documented; the policy says so by pointing to RevenueCat's privacy policy rather than stating a period. (d) Production: the secret key and project id, migration 0012 and both functions are **not** deployed there.

**Existing customers: dry run only (nothing deleted).** Development project, 24 customers: **5 matched to an account** (all 5 current accounts), **14 anonymous** (installs that never signed in; not account-linked; not candidates), **5 orphans** left by earlier deleted accounts (`1196c0b7…`, `1fe67cab…`, `795dd262…`, `c1245172…`, `028b609d…`). Every orphan has **no active entitlement, no purchases and no subscriptions**, so all five are "candidate: no purchase data". The three throwaway customers were removed by the tested flow, leaving the counts as before. The checks were made read-only through the RevenueCat connection; `revenuecat-backfill-dryrun.py` does the same from a key at a hidden prompt and cannot delete (a unit test enforces that). Its purchase and subscription checks need two extra read permissions on a key, so with the delete-only key it reports "review: a check was unavailable" instead. **No deletion of existing customers has been run or written.** Production's 27 customers (7 account-id, 20 anonymous) are unmatched until a read of production accounts is approved.

## 9. Automatic cleanup in development (2026-10-10) and the limits the privacy wording states

**Schedule (development only).** `pg_cron` runs `net.http_post` (`pg_net`) against `revenuecat-cleanup` every 30 minutes. The service key it presents is in Supabase Vault, not in the job text, a migration or the repo (`supabase/dev/schedule-revenuecat-cleanup.py apply|status|remove`; it is deliberately not a migration, which would also run on production). **Verified:** with a one-minute test cadence the job ran on its own and every run succeeded (`cron.job_run_details` = succeeded, the HTTP answer HTTP 200 with the summary); a throwaway account's request that was `accepted` at deletion was moved to `verified` by a scheduled run, with no action from anyone. The cadence was then set to every 30 minutes; the first 30-minute run is recorded under section 10.

**The limits (all real behavior, now stated in the policy).**
- Retry: the sweep runs every 30 minutes; a request still present 15 minutes after being accepted (or a failed one) is requested again, **up to 10 attempts in all**.
- Unresolved: after 10 attempts automatic re-requests stop, the row stays (status not `verified`), the sweep keeps looking the customer up each run and verifies it if it disappears, and the sweep reports a `needsAttention` count (rows out of attempts, or still unverified after 24 hours, for example because the key stopped working) and logs an error line. **There is no automatic alert**: a person must look. Owner check (weekly, and before and after any release): in the SQL editor, `select app_user_id, status, attempts, last_error, first_requested_at from revenuecat_deletion_requests where status <> 'verified' order by first_requested_at;` and the `revenuecat-cleanup` function logs; an old row means resolve it in the RevenueCat dashboard by hand (the customer id is the row's `app_user_id`).
- Retention: verified rows are looked at again for 7 days (a customer can reappear), then **kept until 30 days after verification** and removed by the sweep. Unresolved rows are kept until resolved.

**Privacy wording (in `site/privacy/index.html`, still highlighted as pending).** Collection: before sign-in the app may create a random installation identifier with RevenueCat (device and app information, no name, email or account ID), linked to the account at sign-in; link to RevenueCat's privacy policy. Deleting your account: we ask RevenueCat to delete the customer record, including purchase history and the linked installation identifier; it is not instant; an automatic check every 30 minutes confirms it and repeats the request, up to 10 attempts, and checks again for 7 days in case it is recreated; a minimal record (old account ID and status only) is kept meanwhile and deleted 30 days after confirmation; if it still cannot be confirmed after 10 attempts, automatic retries stop, the record is kept and we resolve it by hand; no need to contact us; an installation that never signed in is not linked to any account; deleting the account does **not** cancel an App Store subscription. **It stays pending until production has the same implementation and the same schedule, verified.**
